## The app process

The sections above time what the UI waits on. This one is about the Rust process as a whole, while you use it and while it sits in the background: how long launch takes on the Rust side, how much memory it keeps, and how often it wakes the CPU when there is nothing to do. It is hand-written from the measurements below (`docs/perf/app-process.md`, pasted in by the report script), not produced by `scripts/bench.sh`.

**How it was measured.** The release build of the app (`lto`, `codegen-units = 1`, the frontend embedded) ran on the shared Linux build VM under Xvfb with WebKitGTK, pointed at the 100k-message synthetic mailbox from `bench.sh` (`PENGUIN_DATA_DIR`), with a search-by-meaning index of 200,000 vectors and the model files in place. No account can sync there (no Keychain), so these are the local parts only. A sampler read `/proc/<pid>` once a second: resident memory split into anonymous (the heap: what the process really holds) and file-backed (SQLite's memory maps of `penguin.db` and `semantic.db`, which the OS can drop at any time and which macOS doesn't count in an app's memory footprint), threads, and each thread's context switches; a context switch of a thread that was asleep is a wakeup. "Before" is commit `487abde` (main plus the launch milestones below); "after" is this branch. Every number is the median of three runs, before and after alternating; idle windows are 3 minutes starting 45 s after launch.

### What changed

| | Before | After |
|---|---:|---:|
| Timer wakeups per hour at idle from Penguin's own tasks, one account (by design, below) | ~4,000 | ~2 |
| … each further account | +3,600 | +0 |
| Wakeups per minute of the app's own threads at idle (Tokio workers, blocking pool, indexer; measured) | 35 | 0 |
| Short-lived threads started per idle minute (measured) | 3.3 | 0 |
| CPU spent checking the model files at every launch | 1.47 s (217 MB read and hashed) | 0–4 ms |
| Heap while the search model is loaded, after indexing | 470 MB | 259 MB |
| Heap after the model is unloaded (10 idle minutes) | 339 MB | 84 MB |
| Peak heap during model load and indexing | 470 MB | 394 MB |

**Timers that polled for nothing.** Apple: "Timers prevent the CPU from going to or staying in the idle state, which increases energy usage and consumes battery power", apps should respond to events instead of polling, and "forgetting to stop timers probably wastes more energy than anything else in OS X" ([Energy Efficiency Guide for Mac Apps, Minimize Timer Usage](https://developer.apple.com/library/archive/documentation/Performance/Conceptual/power_efficiency_guidelines_osx/Timers.html)). What the process did every hour with nothing to do, and what it does now:

| Task | Before | After |
|---|---|---|
| Sync progress heartbeat (Gmail, IMAP, Microsoft), per account | a 1 s interval for the life of the account: 3,600 wakeups/hour, each checking "am I backfilling?" | waits on the phase itself (`penguin_provider::heartbeat`, a `watch` channel); ticks only while backfilling |
| Fact extraction for Ask (`extract.rs`) | every 20 s: 180/hour, each a new blocking-pool thread (idle ones exit after 10 s) and a probe of the unextracted index | sleeps on `AppState::mail_changes`, a counter bumped by sync and by the app's own mail changes; a burst settles 2 s, then one pass |
| Invitation scanner (`calendar/invites.rs`) | every 60 s: 60/hour | the same signal; again after 60 s only while a round leaves work (a full batch of 25, or offline) |
| Search-by-meaning indexer, caught up (`semantic/mod.rs`) | every 60 s: 60/hour | sleeps until its next deadline (the 30-minute full pass, or unloading the model 10 minutes after its last use); everything else pokes it |
| Send later, reminders, snooze (`outbox.rs`) | every 60 s: 60/hour | no timer when nothing is scheduled; a timer capped at 60 s when something is (monotonic timers don't advance while the Mac sleeps: [`Instant` on Darwin is `CLOCK_UPTIME_RAW`](https://doc.rust-lang.org/std/time/struct.Instant.html)) |
| Rules (`rules/runtime.rs`) | every 60 s: 60/hour | the same, for scheduled rules |

With the mail view open and idle, the whole process now wakes about 30 times a minute on this VM, all of it GTK and WebKitGTK (the main loop, ~12/min, and WebKitGTK's memory-pressure monitor, ~15/min), which WKWebView on macOS doesn't share; Penguin's own threads didn't wake once in 3 minutes. Still on timers, because there is no event to wait for: Gmail's history poll (every 30 s per account, a network request; owned by the sync engine), the calendar poll (5 min), contact photos (hourly), update checks (6 h) and the WAL checkpointer (250 ms after a write, then nothing).

**Checking the model on every launch.** The 217 MB of model files were hashed at every start, before search by meaning could be used, even though the model itself loads lazily: 1.47 s of CPU and a full read of the files. `model::verify_cached` hashes only what changed since the last full check: a stamp beside the files records each one's size, inode, and modification and change times. A write, replace, `touch` or `chmod` moves a file's change time, which user space can't set back, so the file is hashed again; files younger than 2 s aren't stamped, the "racy git" rule ([git-scm.com/docs/racy-git](https://git-scm.com/docs/racy-git)) for filesystems with coarse timestamps. Now the check takes 0–4 ms.

**Memory left behind by the model.** Loading the model parses a 20 MB `tokenizer.json`. Measured alone (glibc), the parse peaks at 391 MB, and when it returns the tokenizer holds 68 MB (glibc's in-use count) while the process holds 287 MB: the rest is freed temporaries the allocator keeps for reuse. After the idle unload, the whole model's pages stayed resident the same way: 339 MB of heap in the app with nothing in it, against 53 MB for an app that never loaded the model. Now it is 84 MB after the unload (the extra ~30 MB over a never-loaded app matches the standalone test, where loading and dropping the session and tokenizer left 29–30 MB after a trim: ONNX Runtime's process-wide state once initialized, plus fragmentation) and 259 MB while the model is loaded after indexing. `memory.rs` asks the allocator to return free pages after the model loads (9 ms), after it is dropped (25 ms), and after a sweep that embedded anything (3 ms): `malloc_zone_pressure_relief(NULL, 0)` on macOS, which examines every zone and "returns the number of bytes released" ([`<malloc/malloc.h>`](https://opensource.apple.com/source/libmalloc/libmalloc-283.100.6/include/malloc/malloc.h.auto.html); Penguin logs that number as `released free heap mb=…`), and [`malloc_trim(0)`](https://man7.org/linux/man-pages/man3/malloc_trim.3.html) on Linux, which releases free memory anywhere in the heap, not only at its top.

**ONNX Runtime's arena.** Each passage batch grows ONNX Runtime's CPU arena to that batch's peak, and the arena keeps it: in a standalone test (the model loaded with the app's session options, 20 queries, then 30 batches of 16 passages) the heap went from 172 MB loaded to 255 MB after indexing and stayed there. ONNX Runtime's arena shrinkage "allows users to 'shrink' the arena at some cadence. Currently, the only supported cadence is at the end of every Run()" ([ONNX Runtime C API, memory arena shrinkage](https://onnxruntime.ai/docs/get-started/with-c.html)). With `memory.enable_memory_arena_shrinkage = cpu:0` on the passage runs and a release afterwards, the heap after indexing was 173 MB. Batch time didn't get worse (median of the three runs' medians: 4.73 s shrinking, 5.07 s not, per 16 passages on this VM; queries 52 vs 60 ms), and the real-model tests (`tests/real_model.rs`: retrieval on the eval set, queries preempting passages without changing results) pass. Other settings measured the same way and not taken: turning the arena off left glibc holding 1.4 GB after the 30 batches (fragmentation; 172 MB after a trim), `with_memory_pattern(false)` and device-allocated initializers changed nothing (255 MB).

**No allocator swap.** Same tokenizer test, loaded → dropped, three runs each: glibc 287 → 94 MB (1 MB after `malloc_trim`), [mimalloc](https://microsoft.github.io/mimalloc/) 326 → 326 MB (it purges freed pages after a delay, on later allocator activity), [jemalloc](https://jemalloc.net/jemalloc.3.html) 253 → 203 MB (its dirty pages decay over `dirty_decay_ms`, 10 s by default). The only allocation-heavy moment where the allocators differed, the difference was the retained free memory, and the fix for that is the release call, which works with the system allocator on both platforms. ONNX Runtime suggests mimalloc for speed ("single- or double-digit improvements in performance" depending on the model; [Memory consumption](https://onnxruntime.ai/docs/performance/tune-performance/memory.html)), but that means building ONNX Runtime with it; linking a Rust global allocator doesn't reach ONNX Runtime's C++ allocations. macOS's allocator returns pages differently from glibc, so the Mac numbers need the script below.

**Background work at utility QoS.** Fact extraction (the first pass reads every message: 16.5 s of CPU per 100k messages here, spread over about a minute) and the verification-code backfill now run at utility QoS on macOS (`qos.rs`), like the embedding threads already did. Apple: "Optimally, run your app at a QoS level of utility or lower at least 90% of the time when user activity is not occurring", and QoS sets "scheduling, CPU and I/O throughput, and timer latency" ([Prioritize Work at the Task Level](https://developer.apple.com/library/archive/documentation/Performance/Conceptual/power_efficiency_guidelines_osx/PrioritizeWorkAtTheTaskLevel.html)). Both take the store's writer lock for short transactions; std's `Mutex` is a pthread mutex on macOS, and "when `pthread_mutex_lock()` is called while the mutex is held by a thread with lower QoS … the thread holding the lock is raised to the QoS of the caller" ([Prioritize Work with QoS, priority inversion](https://developer.apple.com/library/archive/documentation/Performance/Conceptual/EnergyGuide-iOS/PrioritizeWorkWithQoS.html)), so user actions don't queue behind them. The pool thread's class is restored afterwards.

### Launch

`penguin.log` has `launch ms=… step=…` lines, milliseconds since `run()` started: `setup started` (the webview and window exist), `database open` (`AppState::init`: settings, the mail database and its migrations), `setup done` (every background task spawned), `page loaded`, `first rows` (the first `list_threads` answered). Medians on this VM: `setup started` 204 ms (Tauri, GTK and WebKitGTK start-up), `database open` 9 ms later, `setup done` 12 ms after that, `page loaded` at 538 ms and `first rows` at 871 ms. Everything slow is off that path:

- **The vector index** loads on the indexer's own thread at utility QoS: 0.56–0.77 s for 200,000 vectors here (28 MB in RAM). Two thirds of that is `f32::round` in the int8→int4 repack, a libm call on baseline x86-64 and a single instruction (`FRINTA`) on arm64, so the Mac should be several times faster (`semantic index opened ms=` in the log). Search is keyword-only until it's loaded. It does compete a little with the first screen on this VM: `first rows` came at 871 ms with the index loading at launch and 817 ms with search by meaning turned off (medians of five runs each; the ranges overlap, 729–1551 vs 703–872 ms). Deferring the load until after the first rows would buy at most that, at the price of keyword-only search for the first second, so it was left as is; check it on the Mac, where the load itself should be much shorter.
- **The model** loads only when indexing or a search needs it (2.9–3.2 s here, 1.8 s of it parsing `tokenizer.json`), and search stays keyword-only meanwhile instead of waiting.
- **Fact extraction** starts 15 s after launch; the invitation scanner, contacts and calendar 20–30 s after.
- **The verification-code backfill** holds the writer for ~15 ms once caught up.

### Memory at rest

With the 100k mailbox open, caught up and the model not loaded: 53 MB of heap, of which 28 MB is the int4 vector index. SQLite's own heap peaked at 35 MB after a full extraction pass, well under its page-cache limits (64 MiB writer, 32 MiB per reader); reads go through the memory map ([SQLite: memory-mapped I/O](https://www.sqlite.org/mmap.html): pages are used in place "without having to copy anything"), which is why file-backed RSS is a few hundred MB and the heap is small. File-backed pages are clean and reclaimable; Apple's physical footprint, what Activity Monitor shows, counts the dirty and compressed memory a process owns ([Gathering information about memory use](https://developer.apple.com/documentation/xcode/gathering-information-about-memory-use)).

### Threads

21–23 threads at idle on this 8-vCPU VM: Tauri's Tokio runtime (one worker per core, [Tokio's default](https://docs.rs/tokio/latest/tokio/runtime/struct.Builder.html#method.worker_threads)), GTK/WebKit's own, the indexer and the WAL checkpointer. A Tokio worker with nothing to do parks without a timer, so the count costs a few KB of stack each, not wakeups (0 per minute measured), and it wasn't capped; on an 18-core Mac that is 18 parked workers. What did cost wakeups was the blocking pool: its threads exit after 10 s idle ([`thread_keep_alive`](https://docs.rs/tokio/latest/tokio/runtime/struct.Builder.html#method.thread_keep_alive)), so the 20-second extraction poll started a new OS thread each time. ONNX Runtime's intra-op threads (up to 4) exist only while the model is loaded and sleep between runs (spinning off).

### Binary size

The Linux release binary is 59.5 MB (24.7 MB gzipped): 45.9 MB of code, of which ONNX Runtime's static library is the largest part (its archive holds 36 MB of code before the linker drops unused sections); this branch adds 15 KB of code. It is already built with `lto = true`, `codegen-units = 1` and `strip = true`. ONNX Runtime can be built with only the operators one model uses ([reduced operator kernel builds](https://onnxruntime.ai/docs/build/custom.html)), which typically cuts it to a few MB; that means building ONNX Runtime ourselves instead of linking pyke's prebuilt library, so it's an option, not done. `panic = "abort"` and `opt-level = "s"` would also shrink it, at the cost of crash isolation and speed, so they weren't taken.

### Found, not changed here

- **First-run setup keeps a frame clock running.** With the setup screen open and idle, WebKitGTK's display-refresh thread woke ~2,450 times a minute (41 Hz) and the main thread ~900; with the mail view open, neither ran. Something on that screen animates continuously (the focused address field's caret is the likely candidate). It only matters while setup sits open; for the UI owner.
- **Gmail's 30-second history poll** is the one remaining per-account timer at idle (120 wakeups and requests an hour per account). Push (Gmail `watch` via Pub/Sub) needs a server, which Penguin doesn't have; a longer interval while the window is hidden would trade freshness. Sync engine owner.
- **`tokenizer.json` parsing** is 1.8 s of the 3 s model load and the 391 MB peak. A pre-parsed tokenizer would cut both. Embedding owner.

### On a Mac

Not measured on macOS yet: idle wakeups with WKWebView, the physical footprint and what `malloc_zone_pressure_relief` returns, the effect of utility QoS, and index load time on arm64. `scripts/process-stats.sh` measures them on a running Penguin: the last launch's milestones and `released free heap mb=…` lines from `penguin.log`, the physical footprint, threads, and CPU, idle wakeups and energy impact over five idle minutes (`top` in delta mode), plus per-app energy under `sudo` (`powermetrics`, which also counts WKWebView's web-content process with the app). Run it three times:

1. Quit Penguin, open it, wait until it's caught up, then `scripts/process-stats.sh` (leave the Mac alone for five minutes).
2. Search for something (the model loads), wait a minute, run it again with `60`.
3. Leave Penguin alone for 11 minutes (the model unloads), run it again with `60`.

Expect, if the Linux results carry over: no idle wakeups from Penguin's own threads, `semantic index opened ms=` well under the 0.6 s here, and a footprint after step 3 close to step 1's.
