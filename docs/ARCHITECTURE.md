# Penguin architecture (MVP)

Goal of the MVP: one person uses Penguin daily with **several Google Workspace / Gmail accounts** (three in the reference setup). It has a unified inbox, fast keyboard triage, and **instant local search over the whole mailbox**. There is no Penguin server.

```
┌──────────────────────── Tauri 2 app (macOS first) ─────────────────────────┐
│  React + TS UI (apps/desktop/src)                                          │
│    inbox · thread · search overlay · ⌘K palette · compose · onboarding     │
│    talks ONLY through src/lib/api.ts  ──invoke()/events──┐                  │
│                                                          ▼                  │
│  src-tauri (commands.rs, state.rs)  — thin glue, no business logic         │
│      │  every mailbox call: state.provider(account) → MailProvider         │
│      ▼                                                                      │
│  penguin-provider (the seam: MailProvider/Backend, compose, outbox, snooze) │
│      │  implemented by                                                      │
│      ▼                  ▼                     ▼                             │
│  penguin-gmail      penguin-core          penguin-render                    │
│  OAuth+PKCE         SQLite (WAL)          ammonia sanitizer,               │
│  Keychain tokens    FTS5 search           remote-image/tracker block,       │
│  Gmail REST         query parser          iframe-ready HTML doc             │
│  sync engine        thread views                                            │
└──────┬─────────────────────────────────────────────────────────────────────┘
       │ HTTPS (device → Google directly)
       ▼
   Gmail API  (gmail.modify scope, per-account refresh token in macOS Keychain)
```

## Decisions
- **Tauri 2 + Rust core + React/Vite.** No Next.js. The core crates don't depend on Tauri.
- **Gmail API, not IMAP.** We use `format=full`, sync newest-first, and resume from a saved page token. `history.list` polling every ~30s handles incremental changes. Pub/Sub push needs a server, so it's out.
- **SQLite + FTS5 for search in the MVP**, all in one transactional DB. Search sits behind `Store::search`, so Tantivy can replace FTS5 if benchmarks favor it. Encryption at rest (SQLCipher) is a follow-up; the file lives in the app's data dir under FileVault.
- **Attachments are never downloaded during sync.** Only metadata and filenames are indexed. Bytes are fetched on demand.
- **Optimistic actions.** Archive, star and similar actions update the local DB immediately and emit `mail-changed`, then call Gmail. On failure the change is reverted and the UI is told. The UI is optimistic too, one step earlier: it changes rows, cached threads and unread counts before `modify_threads` even returns, re-applies the change over any backend read that may predate it until the call settles, and reverts if the call is refused (`src/app/store.ts`, `src/app/optimistic.ts`). Opening an unread conversation marks it read in the same frame, except a hidden-from-All account's mail opened from outside that account's own list (search, person card, notification, a link: `ui.selectedOutside`, `allInboxes.marksReadOnOpen`). Marking the open conversation unread (U, ⇧U, the toolbar's Mark unread, the message menu) keeps it unread: the full view goes Back with the cursor on it as `selectedByApp`, the reading pane stays (`ui.leaveMarkedUnread`).
- **Rendering.** Email HTML is sanitized in Rust by penguin-render, then shown in an `<iframe sandbox srcdoc>` with no scripts, no same-origin and a deny-by-default CSP. Remote images are blocked until you click "Load images".
- **Private-first OAuth.** Each user creates their own Google Cloud "Desktop app" OAuth client (see `docs/google-setup.md`). The client JSON sits in the app config dir; it is never committed.

Sync window (`penguin-gmail/src/sync_window.rs`, `src-tauri/src/sync_window.rs`, Settings → Sync): `syncWindowMonths` (1/3/6/12/24, 0 = everything; default 6) of mail is downloaded in full; `olderMail` (headers default / none / full) decides the rest. Search dates: free text is never interpreted as a date, so "february" or "last spring" typed bare are search words. Date filters come only from `date:` (plain language or explicit: `date:february`, `date:"last spring"`, `date:"jan 5 to jan 20"`, `date:2026-02`; grammar in `penguin-core/src/dates.rs`; months and weekdays mean the most recent past one, and "last <month>" the one before) and from `before:`/`after:`/`older_than:`/`newer_than:`. An unreadable `date:` value becomes a chip of kind `error` ("Couldn't read that date") that constrains nothing. `penguin_core::query::date_hint`/`is_date_like` back the UI's "Use 'february' as a date? → date:february" hint.

Search operators (full reference: `docs/SEARCH.md`; `⌘/` in the overlay): the parser (`query.rs`) builds a boolean tree from terms, `OR`, `AND`, `( )` and `-( )`, then flattens it to AND-of-OR clauses (De Morgan for negated groups; more than 64 clauses is an `error` chip), so `search.rs` compiles one shape: FTS for words and people fields, SQL predicates for the rest. Relationship operators read derived data: `is:new-sender`/`from:new` and `is:first-outbound`/`to:new` look the message up in `first_contacts(email, dir, msg)` (first received from / first sent to each address; schema migration appended to `MIGRATIONS`, backfilled in SQL, kept current on insert, purge and SENT/DRAFT/SPAM relabels, recomputed from `messages_from` or `sent_recipients` when the first message goes; `store_contacts.rs`), and `is:unanswered`/`is:replied`/`is:awaiting`/`is:reply` check later or earlier messages of the same thread via `messages_thread`. Plain English is UI-side and deterministic (`features/search/nl.ts`): a confident phrase ("new senders last week") runs as its operator query, shown as "Understood as …" with Tab to edit and "Search the words instead"; the backend only ever sees operators. The Gmail translator (`penguin-gmail` `to_gmail_query`) drops the local-only operators and marks the query approximate.

Drafts: Gmail mints a new message id on every draft update while the draft id stays fixed, so penguin-core keeps a `drafts(account_id, draft_id, message_id)` table (schema v2; `Store::set_draft` / `draft_for_message` / `message_for_draft` / `remove_draft` / `replace_drafts`). Flows live in `penguin-gmail/src/drafts.rs`, generic over `DraftApi` (GmailClient in the app, a fake in tests). Drafts created elsewhere have no mapping until `get_draft` needs one; then the whole mapping is refreshed from drafts.list.

Replies and forwards (`src/features/compose/{draft,quote,quoteDom}.ts`, `penguin-provider/src/quote.rs`, `src-tauri/src/outgoing.rs`): the composer fills recipients, subject and a text quote from the local thread at once, then `loadOriginal` asks `quote_sources` for the original's sanitized HTML (and a forward's files); until that's back, or the user picks "Send without them" after a failed download (inline error with Retry under the attachments), Send and Send later refuse, so a forward of headers-only mail never goes without its files. The quote goes out in Gmail's markup: a forward is `<div class="gmail_quote">` with the "Forwarded message" block in `div.gmail_attr` and the original's HTML; a reply is the attribution in `div.gmail_attr` plus `<blockquote class="gmail_quote">` (both classes are in the composer allowlist). The text part keeps the plain header block / `>` quote. Reopened drafts get the quote's HTML back from their HTML part (`quoteFromHtml`), so autosave and restarts keep the formatting (styles reduced to the editor allowlist). Forwarding a conversation (F, the menus, the reply dock: `composeContext.whole`) forwards its latest non-draft message and offers the other messages' files (deduped by name and size) under "Also attach N files from earlier messages", on by default when the forwarded message has none of its own; a message's own Forward button forwards just that message and its files. Inline images (`penguin-provider/src/inline.rs`, `src/features/compose/{inline,inlineSrc}.ts`, `editor/imageView.ts`): an outgoing attachment with a `contentId` is an inline image when the HTML shows it (`<img src="cid:…">`). `compose` then sends `multipart/alternative` (text, then `multipart/related` with the HTML and each image with its `Content-ID`) inside `multipart/mixed` when there are files; one the HTML doesn't show goes as an ordinary file, and plain-text mail sends every image as a file. Graph uploads them with `isInline` + `contentId`. Ids are minted fresh (`img-<24 hex>@penguin`) and only `[A-Za-z0-9._@+=-]` ids are ever written into HTML or a header. The composer: an image pasted or dropped into the body (PNG/JPEG/GIF/WebP/BMP/AVIF, ≤10 MB each; bigger ones attach, with a toast) becomes an attachment with a fresh `contentId` plus an `inlineImage` node (`cid`, `alt` = file name, `width` = its own, capped at 600) shown at that width and never wider than the text; the picture comes from a registry by cid (the pasted bytes, or `preview_attachment` for a reopened draft's parts), never from the document. The attachment row lists files only; the 25 MB limit counts images too. `toDraft` sends only the inline images the final HTML shows, so a deleted image stays in state for ⌘Z but never goes out. Replies and forwards attach `quote_sources`' `inlineImages` with the quote, so the quoted original keeps its inline pictures; remote images in a quote stay dropped (SECURITY.md → Rich-text composer). Drafts keep images across save and reopen on Gmail, IMAP and Graph (`DraftRef.attachments` re-points them by Content-ID).

Rules & automations (`src-tauri/src/rules/`, `penguin-core/src/store_rules.rs`, UI `src/features/rules/`, Settings → Rules): definitions in `<config dir>/rules.json` (atomic 0600 write, like settings.json); `{trigger, condition, actions[], scope, dryRun, stopProcessing, includeBody}`. The condition is the search language, matched by `Store::match_query` (same parse + compile as search; unranked, every message) restricted to the event's message ids. Triggers: new mail (`SyncObserver::messages_added`, history.list only, never backfill), label added (`labels_added`, or new mail arriving with the label), daily/weekly schedule (local time; a missed slot runs once at launch), manual. The observer appends to the durable `rule_queue` before the history cursor moves, so a crash replays instead of losing events; the rules task drains it in its own tokio task (never blocks sync). A live rule claims `(rule, message)` in `rule_applications` before acting (never fires twice; claims left pending by a crash become `interrupted`, not retried). Thread actions go through `commands::apply_thread_action` (the modify_threads path: optimistic, Gmail in the background, undo via inverse actions). Dry-run logs only (hooks don't run). Limits: a sync-triggered rule acting on >500 messages/hour is paused; forwards ≤20/hour, ≤100/day; runs ≤1,000 messages. Hooks/webhooks are off unless `allowHooks`: programs get argv exactly as typed (absolute path, no shell, env cleared to a minimal base + id-only `PENGUIN_*`), the match as `ruleMatch` v1 JSON (`docs/cli-schemas/ruleMatch.v1.schema.json`, CLI `MessageOut` messages; text only with `includeBody`) on stdin, killed at the timeout; webhooks POST the same JSON, no redirects, `X-Penguin-Signature: t=<secs>,v1=<hex HMAC-SHA256(secret, "t.body")>`. Per-rule history lives in `rule_log`; every row is also appended to `<log dir>/rules-audit.log` (ids and action outcomes only). Conditions with an unreadable `date:` (an "error" chip, which would constrain nothing) or `type:event` are rejected; relative dates (`newer_than:7d`, `date:"last week"`) resolve at evaluation time. A label a rule added is not a label-added trigger for 15 min on that thread (Gmail echoes it through history), so rules can't loop; a label event also requires the message to still carry the label. Rules push at most 240 thread changes a minute to Gmail (the drain waits, nothing is dropped). Known gaps: mail parked after a failed history fetch (stored later by the shared retry pass) and mail fetched by reconcile after `HistoryExpired` doesn't trigger new-mail rules. Rules run only in the app process, never in penguin-cli or MCP. Snooze is not a rule action yet.

Snooze (`penguin-core/src/store_snooze.rs`, `penguin-provider/src/snooze.rs`, `src-tauri/src/snooze.rs` + the loop in `src-tauri/src/outbox.rs`, UI `src/features/snooze/`, `src/lib/mock/snooze.ts`): Gmail has no public snooze API, so a snooze is the normal archive (remove INBOX, optimistic, pushed to Gmail) plus a local row in `snoozes(account_id, thread_id, wake_at, snoozed_at, woke_at, pushed)` (schema `SCHEMA_SNOOZES`, the last migration). The row is written before the archive; if Gmail refuses the archive, the revert puts the thread back in the inbox, which ends the snooze. `MailboxView::Snoozed` (`{kind: "snoozed"}`) lists active snoozes soonest first from `snoozes` (not `thread_views`): one page of up to 1,000, `before` returns nothing, and it honours the account scope and `unreadOnly`. `ThreadSummary.snoozedUntil` is set in every view (a primary-key probe per returned row). Waking runs in the outbox scheduler (one loop: the next pass is the earliest send, reminder or snooze; it sleeps at most a minute, so it catches up after the Mac sleeps, and overdue snoozes wake on the first pass after launch): `Store::wake_snooze` stamps `woke_at` and adds INBOX + UNREAD locally in one transaction, then `threads.modify` adds the same on Gmail. Failures (offline, signed out, rate limited) keep the local wake and retry every 5 min (`pushed` stays 0, `wake_at` holds the retry time); a 404 drops the snooze. A woken thread's inbox views use `max(latest message, woke_at)` as their sort key, so it comes back on top (Gmail does the same), until it leaves the inbox. `refresh_thread` keeps the row honest: a snoozed thread that is back in the inbox before waking (a reply arrived, or it was moved to the inbox here or elsewhere) ends its snooze early, as Gmail does; trash, spam or deletion drop it. Known limits: Gmail's own apps show the thread as archived until Penguin runs and wakes it, and Gmail's native snoozes are not read. UI: H, the row's hover action, the thread toolbar, the context menu and the selection bar open the picker (Later today = 6 PM or ~3 h on, Tomorrow morning 8 AM, This weekend = Saturday 8 AM, Next week = Monday 8 AM, 1–4 to pick, or a date and time; `presets.ts`, `tests/snooze.test.ts`). The toast has Undo (Z) that puts back the previous state (the old snooze time, or the inbox). The sidebar's Snoozed row (G then H, ⌘8, ⌘K) shows the count; rows show "⏰ Tue 8:00 AM" in place of the date; E or Unsnooze in the Snoozed view moves the thread to the inbox. A wake emits mail-changed and `penguin://snooze-woke` (a toast with Open) and shows a macOS notification when the window isn't focused.

Only counts and timings are logged.

Background work and the app process (`src-tauri/src/{startup,qos,memory}.rs`, `penguin-provider/src/heartbeat.rs`; measurements in docs/PERFORMANCE.md, "The app process"): background tasks wait for an event, not a timer, when there is nothing to do. Local mail changes bump `AppState::mail_changes` (a `watch` counter; fact extraction and the invitation scanner sleep on it), the semantic indexer sleeps until its next deadline or a poke, the outbox and rules hold a timer only while something is scheduled, and a sync heartbeat ticks only while its account backfills. Work nobody waits on runs at utility QoS on macOS (`state::background` for blocking-pool work, `qos::utility` inline; the indexer and ONNX Runtime threads already do). After the rare large transients (the search model loads, is dropped, or finishes a sweep) `memory::release_free_heap` hands free heap pages back to the OS; the passage runs also shrink ONNX Runtime's arena. `penguin.log` has `launch ms=… step=…` lines (`setup started`, `database open`, `setup done`, `page loaded`, `first rows`) and `released free heap` lines; `scripts/process-stats.sh` reads them on a Mac with the memory footprint and idle wakeups.

Verification codes (`penguin-core/src/otp.rs`, UI `src/features/otp/`): at ingest, `insert_message` runs a pure detector over the subject and the first ~600 chars of the authored body (quoted history, replies/forwards, sent mail and drafts are skipped). ## Providers and Add account

Research and plan: `docs/providers-and-onboarding.md`. Every provider is bring-your-own: Google with the user's own Cloud client (`docs/google-setup.md`), Microsoft with the user's own Entra app registration, everything else with app passwords or the account password over IMAP + SMTP. Nothing is tied to the maintainer's accounts.

**Detection** (`src-tauri/src/providers/`: `detect.rs`, `table.rs`, `autoconfig.rs`; UI-free, tested against a fake network in `providers/tests.rs`). `detect_provider(email)` normalizes the address (trimmed, domain lowercased, IDN → punycode; accepts `Name <addr>` and `mailto:`), then: (1) the built-in consumer domain table, generated from ISPDB snapshots (gmail.com, googlemail.com; ~100 Outlook/Hotmail/Live domains; Yahoo, AOL, iCloud, Fastmail, Proton), no network; (2) MX through libresolv (`avatars/dns.rs::mx`, 4 s timeout): `smtp.google.com`/`*.google.com`/`*.googlemail.com` → Google Workspace, `*.mail.protection.outlook.com` → Microsoft 365, `*.olc.protection.outlook.com` → Outlook.com, `*.mail.gm0.yahoodns.net` → AOL, `*.yahoodns.net` → Yahoo, `*.mail.icloud.com` → iCloud, `*.messagingengine.com` → Fastmail, `*.protonmail.ch` → Proton; Proofpoint/Mimecast/… MX hosts are reported as `gateway`; (3) autoconfig, fetched in parallel (6 s each) through the avatar service's hardened HTTPS client (public IPs only, ≤64 KB, DTDs refused) and read in Thunderbird's order: `https://autoconfig.<domain>/mail/config-v1.1.xml`, `https://<domain>/.well-known/autoconfig/mail/config-v1.1.xml`, the ISPDB `https://autoconfig.thunderbird.net/v1.1/<domain>`, the ISPDB for the MX host's base domain; an answer naming a known IMAP host (imap.gmail.com, outlook.office365.com, …) takes that provider's flow; (4) otherwise `unknown`. Only the domain ever leaves the Mac. When DNS and every fetch fail, `offline: true` and the answer is not cached; other answers are cached per domain for the session. Logs carry kind and source only.

`DetectedProvider {email, domain, kind, displayName, auth, setup, imap, smtp, source, mxHost, gateway, offline, available}`: `kind` gmail | googleWorkspace | outlookPersonal | microsoft365 | yahoo | aol | icloud | fastmail | imapGeneric | unknown; `auth` googleOAuth | microsoftOAuth | appPassword | imapPassword; `setup` (which instructions) google | microsoft | yahoo | aol | icloud | fastmail | proton | imap | unsupported; `imap`/`smtp` = `ServerSettings {host, port, security: tls | starttls | plain, username}` with usernames filled in (iCloud IMAP = the part before the @); `source` domainTable | mx | autoconfig | ispdb | manual | unknown; `available` = `providers::connectable(auth)`: googleOAuth, microsoftOAuth, appPassword and imapPassword (every auth method).

**UI** (`src/features/onboarding/`): `flow.tsx` (`useAddFlow`) is shared by first-run setup (`index.tsx`, with the rail; progress in localStorage `penguin.onboarding` v2) and the Add account modal (`AddAccountModal.tsx`). Step 1 is the email field with a "Choose provider" picker (Google, Microsoft, Yahoo, iCloud, Fastmail, Other IMAP), which calls `detect_provider(email, choose)`. Paths: Google = the Cloud guide (only when no client is configured) then `add_account(loginHint)`; Microsoft = register the Entra app → Graph permissions → paste the client ID (`set_microsoft_client`) → sign in; Yahoo/AOL/iCloud/Fastmail = provider-specific app-password instructions with a deep link, then the password; Proton = Proton Mail Bridge, then server settings prefilled with Bridge's defaults; Other = server settings (prefilled from autoconfig when known); unknown = "We don't support <domain> automatically yet" with the picker and the manual option (offline: "Couldn't check <domain>" + Try again). Instructions and error texts are data in `providers.ts` (tested in `tests/onboarding.test.ts`). Where `available` is false the last step shows "coming in the next update" instead of the Connect/Sign in button. Mock mode connects everything; `penguin.mock.providersPending` / `penguin.mock.connectFails` show the other states (`src/lib/mock/providers.ts`).

**Provider seam (phase 0, landed).** Brief for the provider agents: `docs/PROVIDERS-IMPL.md`. `crates/penguin-provider` defines `MailProvider` (one account: fetch messages/bodies/attachments/headers/raw source, modify/trash/untrash threads, labels, send, drafts, send-saved-draft, optional server search, window estimates and profile photo) and `Backend` (one kind: per-account clients, Keychain check, sign-out, per-account sync tasks through `SyncObserver`, window policy), one error type mapped to the command codes, and the provider-neutral pieces moved out of penguin-gmail: `compose` (outgoing MIME), `outbox` (send later, reminders), `snooze` (wakes), `window` (policy), plus `ids` (id and label rules), `credentials` (Keychain vaults for IMAP passwords and Microsoft tokens), `fake` and `conformance` (tests). penguin-gmail implements it in `provider.rs` (`GmailProvider`, `GmailBackend`) by delegating to its existing code. The app keeps one backend per `AccountProvider` in `providers/registry.rs` (Gmail's installed when a Google client is configured; others in `providers::install_backends`) and every mailbox call goes `state.provider(account_id)` → the account's `MailProvider`: commands, the optimistic modify path, outbox/send later, snooze wakes, rules (forward), unsubscribe (mailto send, one-click check), sync-window estimates, server search, lazy bodies, attachments, inline images, invites. Google-only features stay on `state.services()` and are gated by `Account.capabilities` (calendar, contact photos; the account photo uses `MailProvider::profile_photo` for other providers). MCP/CLI read only the store; `penguin-cli sync`/`probe` are Gmail developer tools and refuse other accounts.

**IMAP provider** (`crates/penguin-imap`; brief `docs/PROVIDERS-IMPL.md`, §14 there for what it does and how it's tested). Yahoo, AOL, iCloud, Fastmail, Proton Mail Bridge, any IMAP server, and Gmail quick setup (a personal @gmail.com with an app password; the UI's second option under Google). Its own IMAP4rev1 client (`proto` tokenizer that tolerates any extension, `session` commands, rustls with the OS verifier; any certificate only for loopback hosts, plain TCP only to loopback) and a small SMTP submission client (465 TLS / 587 STARTTLS, AUTH PLAIN/LOGIN, Bcc stripped on the wire). Ids: `e:<EMAILID>` with OBJECTID, `gm:<hex X-GM-MSGID>` on Gmail, else `h:` hash of Message-ID + Date + size; threads `gt:<hex X-GM-THRID>` on Gmail, else JWZ-lite (`threading.rs`: Message-ID/In-Reply-To/References, merges through `Store::set_message_thread`, subject-only merging of "Re:" mail without headers within 7 days). Provider tables (`db.rs`, via `migrate_provider_schema("imap", …)`): `imap_locations` (folder, UID → message id + flags/Gmail labels), `imap_msgids`, `imap_subjects`. Folders: special-use attributes, else well-known names (Sent Messages, Deleted Messages, Bulk Mail, …) → system labels; other folders `f:<path>`; a message's labels are the union over its copies. Gmail syncs `[Gmail]/All Mail` (+ Trash, Spam) and maps X-GM-LABELS. Sync (`sync.rs`): anchors (UIDVALIDITY/UIDNEXT/HIGHESTMODSEQ per folder) recorded before backfill; window fill newest first per folder (inbox first) in 50-message commits, older mail headers-only/full/none per Settings; incremental via CONDSTORE CHANGEDSINCE (QRESYNC VANISHED for expunges) or a FLAGS scan + UID diff; UIDVALIDITY change → re-map, never duplicate; a message with no copy left is deleted only after every folder was looked at (moves aren't deletions, and `messages_added` fires only for mail new to Penguin); IDLE on INBOX (Gmail: All Mail) on a second connection pokes the loop, other folders polled every 5 min. Label deltas → STORE \\Seen/\\Flagged and MOVE (COPY + \\Deleted + UID EXPUNGE without MOVE): archive = INBOX → Archive (`\\Archive`, else `\\All`, else a created "Archive"), +`f:X` = move to X, trash/spam likewise; Gmail = STORE ±X-GM-LABELS. Drafts: `d:<random>` draft ids, each save APPENDs to Drafts and removes the previous version (Gmail: via Trash, so no archived copies linger). Sending: SMTP, then the Sent copy is found (servers that file it themselves: Gmail, iCloud) or APPENDed once. Server search: UID SEARCH per folder (X-GM-RAW with Gmail syntax on Gmail). Capabilities: folders (not labels) for every IMAP account, Gmail quick setup included, so the UI offers Move to… there.

Accounts (schema `SCHEMA_ACCOUNT_PROVIDER`): `accounts.provider` (`gmail` | `imap` | `microsoft`, existing rows `gmail`) and `accounts.provider_config` (JSON `ProviderConfig {auth, imap, smtp, clientId, tenantId, host}`, never secrets). `Account.capabilities` is derived from the provider on every read (`AccountProvider::capabilities`, mirrored for mocks in `src/lib/mock/accounts.ts`). Cursors (schema `SCHEMA_SYNC_STATE`): `SyncCursor.provider_state` is the provider's opaque resume state; Gmail's history id and messages.list page token moved into it losslessly as `{"historyId", "backfillPageToken"}` (`penguin_gmail::sync::GmailCursor`); `backfill_done`, `failed_message_ids` and `window` stay generic columns. Provider-owned tables (IMAP locations, Graph folder maps) go through `Store::migrate_provider_schema` (schema `SCHEMA_PROVIDER_TABLES`: per-provider append-only migrations, per-account tables emptied with the account), never `MIGRATIONS`. `Store::set_message_thread` moves messages between threads (IMAP threading merges). Ids are opaque per account (Gmail's unchanged; Graph immutable ids and `conversationId`; IMAP `e:<EMAILID>` or a hash, threads `t:<hash>`); folders and categories map onto the label model with canonical system labels (INBOX SENT DRAFT TRASH SPAM STARRED UNREAD IMPORTANT) and encoded user label ids (`ids::label_id_for_name`). First-run setup (`src/app/setupGate.ts`) shows when there are no accounts, or Gmail accounts without a Google client; IMAP/Microsoft-only users go straight to mail.

**Contract for the Graph and IMAP providers.** The command is registered (`providers/connect.rs`) and the UI already calls it (`api.connectAccount`):

```rust
#[tauri::command]
pub async fn connect_account(
    app: AppHandle,
    state: State<'_, Arc<AppState>>,
    request: crate::providers::ConnectAccountRequest,
) -> CmdResult<Account>
```

- `ConnectAccountRequest {email, kind, auth, clientId?, password?, imap?, smtp?}` is defined in `providers/mod.rs` (deny_unknown_fields; its Debug redacts the password) and mirrored in `types.ts`; a test pins the JSON the UI sends.
- `microsoftOAuth`: browser sign-in with PKCE on the `/common` authority using `clientId` (also saved by `set_microsoft_client`; read it with `providers::ms_client::load`), loopback redirect `http://localhost:<port>` (registered as `http://localhost` on the Mobile and desktop platform), scopes `openid profile email offline_access User.Read Mail.ReadWrite Mail.Send MailboxSettings.Read`, `login_hint` = `email`. It must be cancellable through `cancel_sign_in` (reject with `cancelled`). Consent failures reject with the AADSTS code in the message (`AADSTS65001` → the UI shows the admin-consent link `https://login.microsoftonline.com/<domain>/adminconsent?client_id=<id>`; see `microsoftErrorText`).
- `appPassword` / `imapPassword`: log in to `imap` (and check `smtp`) before storing anything; the password goes to the Keychain next to the OAuth tokens and is never logged. Bad credentials reject `invalidInput` with the server's words; unreachable servers reject `network`. `security: plain` is only acceptable for `127.0.0.1`/`localhost` (Proton Bridge, which also uses a self-signed certificate on STARTTLS).
- On success: `connect::finish` upserts the account (with `provider` and `providerConfig` from the request), starts its sync, emits `sync-status` and returns the `Account`. An address already in Penguin rejects `invalidInput` (checked before the provider step).
- Then flip `providers::connectable` for that auth method; the UI needs no change.

**Microsoft Graph provider** (`crates/penguin-graph`, registered in `providers::install_backends`; `connect_microsoft` / `reconnect` in `providers/connect.rs`). Sign-in (`auth.rs`, `loopback.rs`): authorization code + PKCE on `https://login.microsoftonline.com/common/oauth2/v2.0` with the user's own client ID (no secret), redirect `http://localhost:<random port>` answered on 127.0.0.1 and ::1, scopes `openid profile email offline_access User.Read Mail.ReadWrite Mail.Send MailboxSettings.Read`, `login_hint` = the address; `/me` (and the ID token) must name the typed address, else invalidInput and nothing is saved. Cancellable through `cancel_sign_in`. The refresh token goes to the Microsoft Keychain vault (`co.gluska.penguin.microsoft`), rotated on every refresh; access tokens stay in memory, refreshed single-flight per account, once more on a Graph 401. Errors carry the AADSTS code with Penguin's own text (65001/90094 admin approval, 700016 wrong client ID, 50011 redirect, 7000218 Web platform, 53000 conditional access), never Microsoft's description (it can contain the address); a refused refresh token is needsReauth. Graph (`http.rs`): `Prefer: IdType="ImmutableId"` on every request, at most 4 requests in flight per mailbox, 429/503/504 retried after `Retry-After` (sends only on 429), a 429 that persists → `RateLimited`. Mapping (`folders.rs`, `convert.rs`): inbox/sentitems/drafts/deleteditems/junkemail → INBOX/SENT/DRAFT/TRASH/SPAM (subfolders of Deleted Items and Junk too), archive → no label, Outbox/Conversation History/Sync Issues/Scheduled not synced, other folders `f:<folder id>` named by path, categories `c:<name>`, `isRead` → UNREAD, flagged → STARRED, `conversationId` → thread; `sender_authenticated` only from Exchange Online's topmost Authentication-Results (`dmarc=pass` for the From domain). Label deltas: UNREAD/STARRED/categories PATCH every message of the thread; INBOX, SPAM, TRASH, `f:` are moves (removing INBOX or a folder = move to Archive, created when the mailbox has none; Sent and Drafts never move except to trash); untrash returns your own messages to Sent Items, others to the inbox; the location and folder label are fixed locally right after a move. Sync (`sync.rs`, cursor `{"v":1,"folders":{"<id>":{"deltaLink","next","plain"}}}`): folders inbox first, each one's first delta round newest first (`$orderby=receivedDateTime desc`, plain delta if Graph refuses it), light fields per page, in-window messages fetched in full, older per `OlderMail`; the page link is saved after every page; every 30 s (or on poke) each folder's delta round; a removal is checked by id (still there = moved, gone = deleted), with `graph_locations(account_id, message_id, folder_id)` (provider schema `graph`) deciding which folder's removal counts; 410 re-lists the folder and removes what it no longer holds; growing the window or turning older mail on runs a range pass over `/me/messages`. Drafts (`drafts.rs`): the draft id is the message id (PATCHed in place); replies start from `createReply`; attachments synced per save (≤ 3 MB inline, larger via upload session); `send_saved_draft` checks `isDraft` first so a second call is notFound; `send_raw` creates a draft from the MIME and sends it (ids known). Also `$search` (free text, from/to/cc/subject, attachments, dates), estimates (`$count`, folder totals), `/me/photo/$value`. Tests run against `fake_graph.rs`, an in-memory Graph and token endpoint behind the transport seam, including `conformance::run`.

## Logging

`src-tauri/src/logging.rs` writes `penguin.log` in the app log dir (`~/Library/Logs/co.gluska.penguin/`, rotated to `penguin.log.1` past 5 MB at startup; `PENGUIN_LOG` overrides the filter). The UI adds what it saw fail through `log_client_event` (`src/applog.rs`, target `penguin_ui`): every rejected command from `call()` in `lib/api.ts` (except answers such as `me_photo` notFound, and `cancelled`), every error toast, and uncaught script errors and promise rejections (`main.tsx`). Identical events are deduplicated per second. Settings → Developer → **View log** (`src/features/logs/`) reads the newest ~1 MB through `read_log`. As everywhere: ids, codes and error text only, never subjects, bodies or tokens.
